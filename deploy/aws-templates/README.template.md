# WeltScout on AWS

Generated by `python3 deploy/aws.py dist` from `dist/vercel.json`. Do not edit the files here: change
`deploy/vercel.base.json`, `deploy/langs.json` or the blog front matter, run `deploy/build.py` and then
`deploy/aws.py` again. Site: {{SITE}}.

What was translated: {{N_RULES}} redirects ({{N_EXACT}} exact, {{N_PATTERNS}} pattern, {{N_SHADOWED}} exact rules
dropped because an earlier rule with the same source or an earlier pattern already answers them, as on Vercel), `cleanUrls`, and the headers.
`aws.py` stops with an error instead of writing a partial translation when `vercel.json` gains a construct it
does not know (`rewrites`, `has`/`missing`, a custom regex, a new header on a path rule, ...).

## Behavior compared with Vercel

- Redirects answer **301** (Vercel answers 308 for `permanent: true`). Same Location, query string appended
  as on Vercel, first matching rule wins, case-sensitive, no trailing-slash tolerance (`/privacy-policy/`
  is 404 on Vercel and here).
- Clean URLs: `/x/` and `/x` serve `/x/index.html`, `/` serves `/index.html`, `/x.html` and `/x/index.html`
  redirect to `/x` (Vercel `cleanUrls`). Both `/sl` and `/sl/` answer 200, as on Vercel.
- Headers on every response (policy `{{POLICY_NAME}}`):

- Per-path headers become S3 object metadata (set by `s3-sync.sh`), everything else gets
  `Cache-Control: {{DEFAULT_CACHE}}` (Vercel's default for static files):

| Files | Headers |
|---|---|
{{CACHE_ROWS}}

## Option A: S3 + CloudFront (recommended)

1. **Bucket**: create a private S3 bucket (Block Public Access on, no static website hosting).
2. **KeyValueStore** (exact redirects), once. Either import the file at creation (upload it to a bucket
   CloudFront can read first):
   `aws s3 cp dist/aws/kvs-redirects.json s3://<bucket>/kvs/kvs-redirects.json` and
   `aws cloudfront create-key-value-store --name weltscout-redirects --import-source SourceType=S3,SourceARN=arn:aws:s3:::<bucket>/kvs/kvs-redirects.json`,
   or create it empty (`aws cloudfront create-key-value-store --name weltscout-redirects`) and fill it with
   `{{KVS_ENV}}=<arn> python3 dist/aws/kvs-sync.py`. Wait until `aws cloudfront describe-key-value-store --name weltscout-redirects`
   shows `READY`; note its ARN.
3. **Build with the ARN**: `python3 deploy/build.py dist && {{KVS_ENV}}=<arn> python3 deploy/aws.py dist`.
   Without `{{KVS_ENV}}` aws.py warns and writes a placeholder id into `viewer-request.js`; never publish
   that file. ARN used for this build: `{{KVS_ARN}}`.
4. **Upload**: `BUCKET=<bucket> {{KVS_ENV}}=<arn> sh dist/aws/s3-sync.sh` with an AWS CLI v2 profile that may
   write to the bucket and update the KeyValueStore (SigV4A). It skips `api/`, `aws/` and `vercel.json`, then
   runs `kvs-sync.py`, which puts new and changed redirects and deletes removed ones (batches of 50).
5. **Function** with the KeyValueStore associated (one store per function):
   `aws cloudfront create-function --name weltscout-viewer-request --function-config '{"Comment":"redirects","Runtime":"cloudfront-js-2.0","KeyValueStoreAssociations":{"Quantity":1,"Items":[{"KeyValueStoreARN":"<arn>"}]}}' --function-code fileb://dist/aws/viewer-request.js`,
   test it (`aws cloudfront test-function` with a request for a redirect source), then
   `aws cloudfront publish-function --name weltscout-viewer-request --if-match <ETag>`.
   A request whose path is not a key falls through to the pattern redirects and clean URLs; a KeyValueStore
   failure is not swallowed (the function errors, CloudFront answers 503) so a broken store is visible.
6. **Headers policy**: `aws cloudfront create-response-headers-policy --response-headers-policy-config file://dist/aws/response-headers.json`.
7. **Distribution**:
   - Origin 1: the S3 bucket (REST endpoint, not the website endpoint) with Origin Access Control; apply the
     bucket policy CloudFront offers. Add `s3:ListBucket` on the bucket for the same CloudFront principal,
     otherwise a missing page answers 403 instead of 404.
   - Default behavior (`*`) to origin 1: Redirect HTTP to HTTPS, GET/HEAD, cache policy `CachingOptimized`,
     response headers policy `{{POLICY_NAME}}`, function association Viewer request = the function above.
   - Default root object: leave empty (the function maps `/` to `/index.html`).
   - Alternate domain `{{HOST}}` with an ACM certificate from us-east-1, then the DNS record (CNAME or alias).
8. **Contact form**: see "Contact form" below (origin 2 + behavior `/api/contact`).
9. **Later deploys**: build, `aws.py` (with `{{KVS_ENV}}`), `s3-sync.sh` (updates the KeyValueStore; a new
   or changed redirect needs no function deploy); only if `viewer-request.js` changed, update and publish it
   (`aws cloudfront update-function` + `publish-function`); `DISTRIBUTION_ID=<id>` makes `s3-sync.sh`
   invalidate `/*`.

## Option B: AWS Amplify Hosting

1. Amplify > Create new app > Deploy without Git; upload a zip of `dist/` without `api/`, `aws/` and
   `vercel.json` (`cd dist && zip -r ../site.zip . -x 'api/*' 'aws/*' vercel.json`).
   With a Git connection instead: build command `python3 deploy/build.py dist && python3 deploy/aws.py dist`,
   output directory `dist`, and put `customHttp.yml` at the repository root.
2. Hosting > Rewrites and redirects > Manage > JSON editor: paste `amplify-redirects.json`.
   Patterns are expanded (`/:lang(hr|en|de)/post/:slug*` becomes `/hr/post` and `/hr/post/<*>`, ...).
   No 200 rewrites are needed: Amplify serves `/x/index.html` for `/x/` itself and answers `/x` with a redirect
   to `/x/` (one extra redirect compared with Vercel, not a 404).
3. Hosting > Custom headers: paste `customHttp.yml`.
4. Contact form: Amplify has no Node function for a static app. Deploy `contact-lambda/` as below and add a
   200 rewrite as the **first** rule: `{"source": "/api/contact", "target": "<Function URL>", "status": "200", "condition": null}`
   (Amplify proxies HTTPS rewrites). Not exercised here; check a POST before going live.
5. Domain management: add `{{HOST}}`.

## Contact form (`POST /api/contact`)

The page posts JSON to `/api/contact` (`fetch("/api/contact", {method: "POST", ...})` in `index.html`), so
the endpoint has to answer on the same host and path; the page needs no change.

1. **Lambda**: Node.js 20 or newer, handler `index.handler`, code = `index.mjs` + `contact.js` from
   `contact-lambda/` (`cd dist/aws/contact-lambda && zip ../contact-lambda.zip index.mjs contact.js`),
   timeout 15 s (each Chatwoot call is cut at 4 s, three may run), memory 128 MB.
   No environment variables: `contact.js` posts to the Chatwoot Client API with its public inbox
   identifier, so there is no key to store.
2. **Entry point**, one of:
   - Function URL, auth type NONE (simplest; CloudFront OAC for Lambda requires the browser to sign the
     POST body with `x-amz-content-sha256`, which the page does not do). The URL is public, like the Vercel
     endpoint.
   - API Gateway HTTP API with route `POST /api/contact` to the Lambda (payload format 2.0); allows throttling.
3. **CloudFront**: origin 2 = the Function URL host (`<id>.lambda-url.<region>.on.aws`) or the HTTP API host,
   HTTPS only. Behavior with path pattern `/api/contact`, precedence above the default behavior, origin 2,
   allowed methods GET, HEAD, OPTIONS, PUT, POST, PATCH, DELETE, cache policy `CachingDisabled`, origin request
   policy `AllViewerExceptHostHeader`, **no** viewer-request function. The viewer-request function also passes
   `{{PASSTHROUGH}}` through untouched in case it is attached there by mistake.
4. Responses (identical to Vercel, the code is the same `contact.js`): 405 for a method other than POST,
   400 `json` for a body that is not JSON, 200 for the honeypot, 422 `invalid`, 502 `send_failed`,
   200 `{"ok": true}`. An accepted submission makes three Chatwoot Client API calls (contact ->
   conversation -> message); a thrown error (Chatwoot unreachable or timed out) is 500, as on Vercel.

## Verify

Against the CloudFront domain first, then the real host (`BASE=https://{{HOST}}`):

```sh
BASE=https://<distribution>.cloudfront.net
aws cloudfront-keyvaluestore describe-key-value-store --kvs-arn <arn>   # ItemCount {{N_EXACT}}, Status READY
curl -sI "$BASE{{SAMPLE_EXACT}}?x=1" | grep -iE '^(HTTP|location)'   # KeyValueStore: 301, location: {{SAMPLE_EXACT_DEST}}?x=1
curl -sI "$BASE{{SAMPLE_PATTERN}}" | grep -iE '^(HTTP|location)'   # pattern: 301, location: {{SAMPLE_PATTERN_DEST}}
curl -sI "$BASE{{SAMPLE_CLEAN}}" | head -1                             # 200 (clean URL, no redirect)
curl -sI "$BASE{{SAMPLE_CLEAN}}/index.html" | grep -iE '^(HTTP|location)'   # 301, location: {{SAMPLE_CLEAN}}
curl -sI "$BASE//example.com.html" | grep -iE '^(HTTP|location)'     # 404 (or 403), never a location to another host
curl -sI "$BASE/" | grep -iE '^(HTTP|content-type|x-content-type-options|referrer-policy|permissions-policy|x-robots-tag|cache-control)'
curl -sI "$BASE/{{SAMPLE_ASSET}}" | grep -iE '^(content-type|cache-control)'
curl -sI "$BASE/llms.txt" | grep -i '^content-type'
curl -s -X POST "$BASE/api/contact" -H 'Content-Type: application/json' -d '{}'   # {"ok":false,"error":"invalid"} (422)
```

A real message (consent true, valid e-mail) sends an e-mail; send one only on purpose.
